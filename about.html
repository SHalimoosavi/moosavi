FOUNDER STORY / THE REASON

Building access
through software.

I build open-source systems because access to capital should not decide who gets to learn, experiment or create useful technology.

“Open source gives people a place to start before they have funding.”

Access is not only about price. It is also about whether a person can understand, run, inspect, adapt and use a system on the device and connection they already have.

Why I build

When someone is starting without financial stability, funding or expensive software, the first barrier is often not imagination. It is access. A paid platform, proprietary tool or large cloud bill can be enough to stop a promising idea before it becomes a working prototype.

Open source creates another path. A person can begin with an existing computer, a local model, a small server, an Android device or a constrained environment. They can study how a system works, adapt it to their needs, share what they learn and build the next useful layer without waiting for perfect conditions.

That is why I build tools across AI, LLM infrastructure, automation, blockchain, OSINT and edge computing. The goal is not to make technology sound impressive. The goal is to make useful capability more accessible, inspectable and adaptable.

How constraints shape the architecture

Memory limits, cost, offline use, small teams and limited hardware are not afterthoughts in this practice. They influence whether a system can run locally, whether dependencies are optional, how much state is retained, how setup is documented and where human approval is required.

Local-first and edge-oriented work is one expression of that principle. Accessibility is another. An interface is not truly accessible merely because it is free; it also needs readable content, keyboard paths, clear states and documentation that a person can inspect.

Open-source principles

01

Start with what you have.

Useful systems should be possible to explore on ordinary hardware and constrained environments where practical.

02

Make the system understandable.

Open source should help people inspect, learn from and adapt the tools they use.

03

Treat constraints as design inputs.

Memory, cost, offline use, limited hardware and small teams should influence architecture from the beginning.

04

Share useful primitives.

A small working tool can become a foundation for someone else’s product, education, research or opportunity.

What I build

Current work spans local LLM infrastructure, software-engineering agents, business intelligence, blockchain engineering research, OSINT tooling, mobile/edge experiments and developer infrastructure. Some systems are active builds, some are research projects and some are experiments.

What I am learning

The work is an ongoing loop of architecture, implementation, testing, documentation and revision. The repository is part of the learning record: what exists, what failed, what is constrained and what comes next should be visible.

How to collaborate

If you are building a product, research system or open-source tool around real constraints, start with the public work and repository evidence. Collaboration can begin with a concrete problem, technical review or shared experiment.

CONTACT

Explore the work, inspect the repositories and start a conversation when there is a concrete system worth building.
